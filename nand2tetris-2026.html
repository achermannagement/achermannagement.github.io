Nand to Tetris course check in 2026

Posted by Joshua Achermann in learning   

Introduction

Back in 2017, I started working on a course that intrigued me. The course was called "From Nand To Tetris" (www.nand2tetris.org) and the premise was fairly simple, starting from a primitive NAND gate can I construct a simple computing core on which to run applications written in a high level language. What has prompted me to continue this course after all this time? For one there is a new edition of the book "The Elements of Computing Systems" [TEOCS2] which contains the coursework. I also recently discovered an updated software web application to test my work, contains some upgrades: nifty!

[TEOCS2]Nisan, Noam, and Shimon Schocken. The Elements of Computing Systems. 2nd ed., The MIT Press, 2021.

My progress to now

From my recollection I got stuck on the latter part of the jack compiler frontend, chapter 11 which is code generation. I plan to go into more depth about the compiler frontend in a later blog post. However I did not have an appetite to learn the Jack language properly (I have been spoilt for developer experience from far more mature languages) so I need to get a grip on that before I consider restarting those chapters. In order to ensure I had a good foundation to finish these last project chapters, I wanted check my understanding of the virtual machine was solid and my translation of the virtual machine to assembly was correct (I was more comfortable with the first half of the course given my specialization in computer engineering so I am not planning on repeating that section of the course).

Code Archaeology

Unfortunately, too often when software engineers are working promptly to get through their backlog, they often will put forward thinking and future concerns of readability and maintainability on the backburner. These concerns include code legibility for the poor sod that will end up looking through the codebase (I cannot imagine that the dawn of vibe coding has helped in this matter, but perhaps that will become less urgent if large language models can be taught to stop hallucinating). It should be no surprise that my younger self would not have been thinking about the long term usage of this VM translator given I was hoping to complete the course before graduating.

So let us take a journey, did a soon to be graduate Joshua produce something is that still comprehensible to a far older, more experienced (and jaded) self?

Now one aspect of this to consider is that had completed each project to the satisfaction of completing a chapter, then copied the script into the next chapter if required and started work on this. So I found two scripts named StackTranslator.py in the project folders labelled for chapters 7 and 8. The course recommended that I make a copy of the script I was working on once I had completed chapter 7 upon starting chapter 8. The first script is much simpler than the second so I tested the first with that chapter before moving to the complete chapter.

Good stuff

I am glad to report the good stuff first.

  • The first VM translator was a python script of roughly 450 lines. The second VM translator was a python script of roughly 600 lines. It had no external dependencies so I evidently didn't outsource my thinking and I was sidestepping the concern of distribution that can plague nascent python projects. It was idiomatic enough python 3.6 code that it ran without modification in the latest stable python (3.14).
  • The final script (the second script is considered the final implementation of the VM translator) is separated into classes Parser and Translator. The script can be invoked directly and the script detects this to run the main method that handles argument parsing and running the translator.
  • Running the script without arguments produced a helpful error message. It has a single argument for passing a filepath. Maybe it was overkill to use argparse from the Python standard library for this purpose, but I haven't seen a downside yet and the user experience is just; nicer than anything I would be able to hand roll without getting distracted from the pedagogy of the course.
  • The second script has some handy debugging tools I must have developed as part of working through these chapters. There was a simple method that generated an infinite loop. It's purpose: a poor mans breakpoint 😆 I could add this infinite loop anywhere and run the CPU emulator until hitting it and the systems state would be frozen (program counter notwithstanding). Here is the method:
def epilogue():
  result = []
  result.append("(HW_INFINITE_LOOP)")
  result.append("@HW_INFINITE_LOOP")
  result.append("0;JMP")
  result = "\n".join(result)
  return result

It defines a label @HW_INFINITE_LOOP and immediately jumps to itself unconditionally which ensures that no state in the system changes from the point this assembly is executed. A simple but effective implementation of a software breakpoint for an emulator of the CPU core.

Failure!

Surprisingly the produced assemblies from these scripts did not successfully load into the new nand2tetris web software. This was strange to me because I remembered that I tested the output of these scripts and they had passed before. The current software is a web application which is pretty nifty, but I used the legacy Java software when I completed these chapters. Maybe the new software was slightly different. Let's drill down into the issues.

In chapter 7, this is when we implemented the stack for the virtual machine. There were tests that manipulate the virtual stack directly in order to test my implementation. I generated the assembly file with my stack translator and got an error upon loading the assembly file into the toolchain. Error loading memory: Line 600: Invalid ASM value: M+D. Did you mean D+M? I was quite surprised because I thought I recalled completing these chapters without seeing this error before. This seems to be a straightforward fatal error that prevent the tests to even run. Investigating further it appears that when I emitted certain addition instructions I did not consistently have the same order in the emitted instruction than the specification. The early emulator was less strict and allowed these instructions and treated them identically (addition is commutative after all). Ensuring that all addition instructions emitted from my solution used the correct operand order fixed this issue.

I cleared the test output from the chapter 8 and regenerated it using the StackTranslator.py script that I found there. There was no errors and the script dutifully produced an assembly file for the FibonacciSeries test vm file. Loading it into the new generation of the nand2tetris tools produced this error: Error loading memory: Line 69: expected "JMP", "JLE", "JNE", "JLT", "JGE", "JEQ", or "JGT" navigating to the offending line in the produced assembly file. 0; JMP which was confusing to say the least, the command is clearly a JMP command. My only theory at the point was that the emulator was objecting to the formatting of the assembly file which was correct. Removing the space between the semicolon and jump instruction fixed this issue .eg 0;JMP (updating the stack translator to produce this formatting from now on in all jump instructions which a simple case of find and replace).

Fixing the formatting of the jump instructions led to the assembly files loading successfully into the emulator. Nice! The course provides a domain specific language of setting up the emulator and running it, which is used to great effect to run tests of our project. I found that when I ran the emulator using the provided test script, the result did not match the expected result. There was a problem in the generated assembly that meant that certain tests were clearly failing despite my recollection that my solution did pass these tests before. After investigating it, I discovered the issue by reading the chapter in the course book again and discovered that some of the tests required me to generate a bootstrap to run the test and others did not. The test I was studying did not need this bootstrap and sure enough, omitting the bootstrap invocation in my translator caused the test to pass again (thankfully I had clearly labelled the method that generated the bootstrap so I could comment it out easily). I had ascertained that I had a working VM implementation in my project work.

Resolution Takeaways

Always use source control

It was so frustrating that I did not version control my attempts! It would have been much easier to determine the progression of the development of the code I would have clearly seen that the were changes required to pass certain tests without having to dredge through the coursebook again! I would have also been able to change between versions of the solution at my leisure so I could more quickly test each stage of my scripts in development.

Document expectations

It is hard to know what you are taking for granted when you embark on a software solution, it is something that can only come with experience. I expect this to be a continuing source of friction people will encounter when using large language models as well, as unconscious expectations will not be communicated the agent will take a reasonable but undesirable path which will be overlooked by the operator. For example, not leaking all the source code when deploying to production (common sense is still mostly a human concept, for now even if we choose not to exercise it!). If I had added a couple targeted comments in certain locations in my solution explaining when to use the bootstrap, it would have saved me half an hour.

Debugging

It is possible to diagnose and resolve issues in legacy code regardless of how underdocumented it is but there is a penalty in terms of time to rework as it will take longer for an unfamiliar developer to get acquainted with the code. I was able to take some heuristics in my debugging journey because I had some latent knowledge of the implementation and even vague recollections can help start the problem solving process in the right direction, but without these sometimes you have to trace the execution of a program at a low level just to identify the fault in the system.

Next steps

Now I am convinced I have completed chapters 7 and 8, next is to tackle using the Jack language itself and unearth my first attempt at the frontend code generation I abandoned previously. This is chapter 9 and my aim to make something relatively meaty with this language so I can understand it further. The main issue I had with this part was lacking some programmer comforts that I am used to in far more mature languages and some small friction with the toolchain, as well as life getting in the way. I was also concerned that my implementation of the virtual machine was not particularly efficient (a concern I still hold and would like to dedicate some time to confirm and resolving that). Once I am happy with my grasp of the Jack language, I want to revisit what I had done with the compiler frontend so far and (probably) rewrite it in order to complete the course to my satisfaction.
