The Ansible Script I desperately want to deprecate

Posted by Joshua Achermann in automation   

My Setup

I use ansible to setup my personal system (this may be overkill, but I find that it meets my needs well 🤷). I find it to be an ergonomic orchestration and automation tool for setting up my Fedora installed computers ever since I have sworn off using Windows as my operating system last year (that could justify its own blog post!).

Not a bed of roses

The ansible platform is very extensible which means it has a lot of potential (just look at how many modules are listed in the documentation). However, that also means there is a lot of surface for potential paper cuts or flaws that escape quality assurance. This is the story of how I encountered one of these paper cuts in the ansible.builtin.dnf (a similar issue occurs in ansible.builtin.dnf5 module). The current version of ansible installed on my current Fedora 44 is 2.20.6 (this is not the absolute latest version of ansible, but c'mon this is bleeding edge Fedora we are talking about here!)

Some astute readers might already be questioning, why I am using this specific dnf module over the generic ansible.builtin.package which could allow my scripts to work with other packaging systems. I agree and would prefer to use the generic module except in this one case, there is a specific dnf feature I want to make use of; groups. Groups under dnf are simply (oh sweet summer child) lists of packages that can be installed with a single group install, the said packages being logically grouped. Here is an example (note: dnf5 output):

If I was packaging software for the Red Hat ecosystem, I would install this package group and would be all set to start. But what if I could add this my ansible dev playbook, so it is available after I first setup my system? It would look something like this.

- name: dev setup
  hosts: localhost
  become: true
  become_method: ansible.builtin.sudo
  tasks:
    - name: Install rpm packaging tools
      ansible.builtin.dnf5:
        name: '@RPM Development Tools'
        state: present

I always run my first time setup scripts on the localhost so I have not abstracted these to roles. I can run this tasks and it reports success, excellent. The system also reports it is installed now.

I hate computers man...

The Complexity Trap

As I have heavily foreshadowed, groups are not simply lists of packages. There is additional metadata to consider, see which types of packages are listed: mandatory, default and optional. I suppose it makes sense that we install the group without including the optional package, but does that really mean the group is installed? I would argue no! In fact a simple is this package group installed? query does not capture the myriad possibilities of a group install, a partial installed state is unfortunately absent. Not the first incomplete abstraction I have seen in my time, but it still frustrating. Anyway, it is straightforward to tell dnf to include optional packages.

dnf group install --with-optional 'RPM Development Tools'

now rpmlint is installed. But how do I pass this flag to the task as it is being run under the ansible module?

  • Check if there is a parameter under the dnf module to pass to the include this flag... Nope
  • Check if there is another module I can use instead... No, I am not going to fallback to shell!
  • Check if there is a back door where I can pass the flag... No, thankfully?

The most _beautiful_ solution is that the dnf module needs to be updated to support package groups robustly, however I have little motivation to ingest the process for contributing to ansible core modules. Furthermore, there are already many stale pull requests to the ansible repo and a drive by pull request from me would be of little value. What I need is a dirty, hacky workaround!

Step back and breathe

What I am actually trying to do? I am trying to install a bunch of packages. Isn't that what my playbooks are doing in the first place? To be fair, I was specifically interested in the group dnf subcommand, but that is not behaving as I want it to, so why limit myself to using it? Hence comes my hacky workaround: automatically generate the playbook that will install all packages in the given package group. We simply bypass the dnf group requirement for my personal playbooks and avoid these increasly complicated model interactions.

Interoperability rules

Ansible playbooks are YAML compliant, which is a well trodden markup language; which means I can work with it with little friction. I have authored a fairly straightforward python project dnf-group-install-playbook that parses the group listing from dnf and emits a YAML script that installs all packages listed in the group. I have since updated it slightly, in order to support dnf5 and to add system metadata in the generated file but the principle is unchanged. The scripts are intentionally minimal, the utility clocks in under 200 lines of python and there are not a lot of features. You simply name the dnf package group that you want to turn into an ansible playbook and the scripts dutifully creates that ansible playbook. You run that playbook with ansible, it will install every package on the target. My parser can differientiate between types of grouped packages, but I don't make use of that. By default, the host is hardcoded to be localhost because that is how I use it.

There is a certain magic that occurs when the user and the implementer align. It is a lot easier when they are the same person 🙂! Perhaps this is the drive behind the bespoke software and vibe coding crazes. This is a piece of software that is simple, trivial even, however it does address a real gap that I felt in my automation of my home Fedora systems. It works exactly the way I need and I have designed it to be extensible, but have not extended towards some perceived need. Prophesying user needs is fraught with risk, it is better just to ask (or be the user 🤣).

Conclusion

I desperately do want to deprecate this project by the way, this project should not have to exist. It is a hacky workaround in response to two faulty abstractions: first the incomplete concept of group installation under dnf, secondly the incomplete implementation of the group install under the dnf ansible modules. It is the defining tension in software around abstraction: abstractions are supposed to make working with details simpler, but a bad abstraction can make things built on those foundation more complicated. These little annoyances that exist during a user session can become fatal when you working with a headless session!
